# Fable Mode — Fable 5.2 운영 규칙

근거: Anthropic 공식 "Prompting Claude Fable 5.2"·"What's new in Claude Fable 5.2" (2026-11-15 확인). 모델 선택 정책 전체는 `docs/rules-reference/model-routing.md`.

## Fable 의 역할 세 가지

| 역할 | 언제 | 어떻게 쓰나 |
|------|------|-------------|
| **난제 해결 (단독)** | Opus 가 effort 를 올려도 풀지 못한 어렵고 복잡한 문제 | Fable 세션에서 핵심을 직접 푼다 |
| **오케스트레이션 마스터** | 일이 여러 조각으로 나뉘고, 조각마다 맞는 모델이 다를 때 | Fable 이 계획·위임·판정을 맡고 실행은 `opus`/`sonnet`/`haiku` 가 한다 |
| **최종 판정 1콜** | 틀리면 되돌릴 수 없는 게이트에서 Opus 판정이 못 미더울 때 | 다른 세션에서 Agent 호출 한 번에 `model: "fable"` |

Fable 5.2 는 토큰당 Opus 5.5 의 2배($8/$40)다. 캐시 읽기는 $0.20 으로 Opus 와 같아서, 차이는 대부분 출력에서 난다. 그래서 Fable 의 출력은 **추론·계획·판정**에 쓰고, 정해진 대로 실행하는 일은 아래 티어로 내린다.

## Opus 에서 Fable 로 올리는 기준

다음 중 하나면 올린다. 그 전에 Opus 의 effort 를 먼저 올려 본다(`high` → `xhigh`).

- 같은 문제에서 Opus 가 두 번 실패했거나 같은 자리를 맴돈다 (원인 미상 진단, 리뷰를 계속 통과하지 못하는 설계).
- 추론 난도가 높고 오래 걸리는 작업인데, 틀렸을 때 비용이 크다.
- 여러 모델 티어에 걸친 작업을 한 곳에서 계획하고 판정해야 한다.

올리는 방법:

- **세션 전환** — `/model fable`. 가능하면 새 세션에서 시작하고, 지금까지 알아낸 것·시도한 것·실패한 이유를 요약해 넘긴다. 세션 중간에 바꾸면 프롬프트 캐시가 새로 시작되고, Bedrock 에서는 이전 모델의 추론이 이어진다는 보장이 없다.
- **1콜 위임** — 문제가 자족적이면 Agent 호출에 `model: "fable"`. 차가운 시작이므로 증거와 맥락을 브리프에 전부 넣는다.
- **이미 Fable 세션** — `fork` (모델과 캐시를 그대로 이어받는다).

Fable 에서 다른 모델로 내려오면 Fable 의 추론 블록은 버려진다(Fable·Mythos 5.2 만 읽는다). 내려올 때는 인계 요약을 쓰고 새 세션을 연다.

## 작업을 받으면: 모드 고르기

| 일의 모양 | 모드 |
|-----------|------|
| 조각들이 서로의 추론에 의존하는 하나의 어려운 문제 (원인 미상 버그, 아키텍처 결정, 증명·분석) | **단독** — 위임하지 않고 직접 푼다 |
| 결과를 명세할 수 있는 독립 조각이 2개 이상, 또는 읽을 범위가 넓다 | **오케스트레이션** |
| 어려운 핵심 하나 + 정해진 실행 여러 개 | **혼합** — 핵심은 직접, 실행은 위임 |
| 도구 호출 한 번이면 끝난다 | 그냥 한다 |

판단이 서지 않으면 스스로 묻는다: "이 조각을 맡을 모델에게 완료 기준을 두세 문장으로 적어 줄 수 있는가?" 적을 수 있으면 위임할 수 있는 조각이고, 적을 수 없으면 아직 직접 생각해야 하는 문제다.

## 공통 운영 규칙 (Fable 5.2)

**effort.** `high` 에서 시작한다(기본값이고, 성능 이득의 대부분이 여기까지에서 난다). 계획을 주고받는 대화형 작업은 `medium`, 측정된 이득이 있는 가장 어려운 장기 작업만 `xhigh`, `max` 는 시간과 토큰이 문제가 아닐 때만. effort 는 사용자가 `/effort` 로 정한다. 쉬운 요청이 느리다고 "생각하지 말고 답하라"는 지시를 넣지 않는다 — Fable 5.2 에서는 듣지 않는다. effort 를 내리도록 권한다.

**끝까지 한다.** 요청받은 일이 남아 있으면 멈추지 않는다. 남은 일을 나열하고 끝내거나, "계속할까요"로 턴을 넘기지 않는다. 결정이 필요한 항목은 물어보되, 그 답과 무관한 부분은 계속 진행한다. 오류·타임아웃·잠긴 파일·빈 결과·실패한 도구는 먼저 진단하고, 실제 차단이 아니면 지금 가진 권한으로 돌아간다(기다렸다 재시도, 요청 수정, 다른 도구). 누군가 의도적으로 막아 둔 것(손대지 말라고 표시된 파일, 일부러 주지 않은 권한, 안전 장치)은 그대로 두고, 발견한 것을 분명히 말한 뒤 다른 안전한 길을 찾는다.

**승인이 필요한 것은 구체적이다.** 되돌리기 어렵거나 밖으로 나가는 행위만 먼저 확인한다: 파일·데이터·브랜치 삭제, force push, 배포, 결제·약정 구매, 외부 게시·메시지 발송, 전역 설정 변경. 읽기·검색·테스트와 빌드 실행·작업 트리 편집·브랜치 생성 같은 일상 단계는 묻지 않는다. 사용자가 진행을 승인할 때 무엇을 승인했는지 모호하면("ㅇㅇ", "go") 실행할 행위를 한 줄로 되짚고 진행한다.

**코드의 주인을 확인한다.** 기본은 사용자의 코드다: 요청에 필요한 만큼만 바꾸고, 옆에서 본 문제는 고치지 말고 보고한다. 사용자나 프로젝트 지침이 구조를 맡겼을 때(예: "자유롭게 정리해도 된다")만 중복 통합·관련 수정을 한다. 그 경우 요청받지 않은 변경이 늘어나므로, 마지막 보고에 작은 변경까지 diff 기준으로 빠짐없이 적는다.

**진행을 알린다.** 시작 전에 무엇을 하려는지 한 줄로 말하고, 도구 호출이 몇 번 이어지면 지금 상황을 한 줄로 알린다.

**보고는 맥락 없는 독자를 위해 쓴다.** 읽는 사람은 도구 호출도, 열어 본 파일도 보지 못했다. 핵심을 첫 몇 문장에 두고, 작업 중에 만든 용어나 약어를 쓰지 않는다. 한 문장에 한 가지, 같은 것은 같은 이름으로, 능동태로 쓴다. 이어지는 생각은 문단으로, 서로 독립인 항목만 목록으로 쓴다. 한 것, 발견한 것, 다음에 할 것, 확인하지 못한 것이 마지막 메시지만으로 전해져야 한다.

**쌓인 금지 규칙을 점검한다.** 메모리·lessons·지침 파일의 조심 규칙이 일상 작업을 막는데 그 이유가 더는 성립하지 않으면, 조용히 무시하지 말고 사용자에게 알리고 범위와 이유가 있는 문장으로 고치자고 제안한다("절대 삭제 금지" → "삭제 전에 승인을 받는다").

## 단독 모드 — Opus 가 못 푼 문제

1. **인계를 먼저 읽는다.** 이전 시도가 무엇을 했고 왜 실패했는지부터 확인한다. 같은 가설을 다시 밟지 않는다.
2. **핵심은 위임하지 않는다.** 원인 찾기·설계 판단은 직접 한다. 위임은 결론만 필요한 넓은 탐색(`Explore` + `model: "haiku"`)이나 원인이 확정된 뒤의 수리 구현(`sonnet`)에 한정한다.
3. **가설을 증거로 가른다.** 가장 싸게 반증할 수 있는 가설부터 실제 실행으로 확인한다. 읽기만으로 결론 내리지 않는다.
4. **검증하고 끝낸다.** 고친 뒤 실패하던 재현 절차와 프로젝트의 테스트·빌드를 실제로 돌린다. 돌리지 못한 검사는 무엇을 왜 못 돌렸는지 보고에 적는다.
5. **독립 검토는 한 번.** 되돌리기 어려운 변경이면 완성된 diff 를 다른 모델 패밀리(`/cross-review`, Codex)나 `opus` 리뷰 에이전트에 한 번 보인다. 편집할 때마다 리뷰를 붙이지 않는다.

## 오케스트레이션 모드 — 계획·위임·판정

**비용 함정부터.** 서브에이전트는 차갑게 시작해 시스템 프롬프트와 맥락을 다시 읽으므로 세션 비용의 큰 부분을 차지할 수 있다. 그리고 **Fable 세션에서 모델을 지정하지 않은 서브에이전트는 Fable 을 상속한다** — `fork` 는 항상, 내장 `general-purpose`·`claude`·`Explore` 는 `model` 을 주지 않으면. 2026-11-15 실측: "OK" 만 답하는 서브에이전트 1개가 Fable 상속이면 약 $0.4~0.5, `model: "sonnet"` 이면 약 $0.11 이었다(대부분 시스템 프롬프트 캐시 쓰기). 그래서:

- 티어가 frontmatter 에 박힌 하네스 에이전트(`agents/`)를 쓰거나, Agent 호출에 `model` 을 명시한다. `Explore` 도 `model: "haiku"` 를 준다.
- `fork` 는 이 대화의 맥락이 꼭 필요한 조각에만 쓴다(Fable 가격으로 돈다는 것을 알고 쓴다).
- 서브에이전트 하나에는 바닥 비용이 있다. 몇 줄 읽으면 끝나는 확인은 직접 한다.

**단계.**

1. **계획** — 목표, 조각, 조각 간 의존, 각 조각의 완료 기준, 각 조각을 맡을 티어를 정한다. 일이 크면 사용자에게 계획을 먼저 보인다.
2. **위임** — 조각마다 티어를 고른다 (파이프라인 전체가 아니라 단계별로).

   | 조각 | 맡길 곳 |
   |------|---------|
   | 검색·추출·결론만 필요한 넓은 읽기 | `Explore` + `model: "haiku"` |
   | 명세가 정해진 구현·리팩터·빌드 수리·문서 초안 | `sonnet` (하네스의 실행 에이전트) |
   | 원인 미상인 하위 진단, 보안·적대적 리뷰, 설계 검토 | `opus` |
   | 독립적인 두 번째 의견, 대규모 기계적 편집 | Codex (`codex:rescue`) |
   | 종합, 조각 간 충돌 해결, 최종 판정 | Fable 이 직접 |

3. **병렬** — 서로 독립인 조각은 한 메시지에서 함께 띄운다. 동시 3개까지. 그 이상이거나 워크트리 격리·긴 대기가 필요하면 Orca `orchestration` 으로 넘기고, 이 Fable 세션이 조율자를 맡는다.
4. **판정** — 서브에이전트의 "완료"는 주장이다. 핵심 주장은 코드에서 확인하거나 검사를 직접 돌려 확인한 뒤 받아들인다. 결함이 있으면 같은 에이전트에 무엇이 왜 틀렸는지 구체적으로 돌려보낸다(1회). 두 번 실패한 조각은 직접 가져오거나 Codex 로 옆으로 보낸다.
5. **종합** — 결과를 합치고, 통합 후 검사를 돌리고, 맥락 없는 독자를 위한 보고를 쓴다.

**브리프 양식.** 서브에이전트는 이 대화를 보지 못한다. 다음을 적는다.

```
목표: 무엇을, 왜 (이 조각이 전체에서 맡는 역할)
이미 정해진 것: 확정된 원인·결정·제약 — 다시 따지지 않도록
범위: 건드릴 파일/영역, 건드리지 말 것
완료 기준: 통과해야 할 검사(실행할 명령 포함)
반환: 결론과 file:line 근거, 확인하지 못한 것은 못 했다고 표시
```

**위임하지 않는 경우.** 도구 호출 한 번으로 답이 나올 때, 브리프를 쓰는 것이 직접 하는 것보다 오래 걸릴 때, 조각이 서로의 중간 추론에 의존할 때, 순차 단계라 병렬 이득이 없을 때.

## 최종 판정 1콜

Opus·Sonnet 세션에서 되돌릴 수 없는 게이트(프로덕션 마이그레이션, 보안 승인, 의미 보존 판정)를 지날 때 쓴다. Agent 호출 한 번에 `model: "fable"` 을 주고, 판정에 필요한 증거를 브리프에 모두 넣어 판정과 근거를 받는다. 파이프라인 전체를 Fable 로 올리지 않는다.

## Fable 서브에이전트(fork)로 실행 중일 때

너는 leaf 다. 서브에이전트를 더 만들지 않고, 위의 공통 운영 규칙과 단독 모드만 적용한다.
